# گزارش اصلاحات و راستی‌آزمایی Audit Trail API v1.2.0

**تاریخ:** ۲۰۲۶-۱۱-۲۱  
**مبنای تغییر:** `audit-trail-api-hardened-v1.1.0.zip`، گزارش ممیزی سخت‌گیرانه نسخه 1.1.0  
**محدوده:** سورس برنامه، schema SQLite، API HTTP، تست‌های رگرسیون، Docker/CI و مستندات استقرار  
**روش:** اصلاح در یک کپی مستقل؛ نسخه 1.1.0 بدون تغییر باقی مانده است.

## حکم

- **عملکرد محلی برنامه:** PASS، در محدوده تست‌های انجام‌شده.
- **برطرف شدن هر هشت یافته ممیزی قبلی در کد/تنظیمات:** پیاده‌سازی و پوشش تست/بازبینی انجام شد؛ برای Docker و Node 24 نیازمند اجرای واقعی روی آن محیط‌هاست.
- **انتشار به‌عنوان پروژه GitHub با بیان محدودیت‌ها:** قابل انجام بعد از تأیید GitHub Actions روی مخزن مقصد.
- **استقرار عمومی حساس یا ادعای Production-Ready:** هنوز NO-GO بدون TLS عملیاتی، محدودیت شبکه، مدیریت کلید، پایش دیسک و قبولی آزمون‌های کانتینری و بازیابی روی محیط مقصد.

## اصلاحات فراتر از هشت یافته

- سناریوی E2E فایل‌محور حالا **تمرین بازیابی واقعی** دارد: پس از ساخت بکاپ معتبر، دیتابیس اصلی را کنار می‌گذارد، بکاپ را به جای اصلی برمی‌گرداند، Verify را اجرا می‌کند و سپس API از دیتابیس بازیابی‌شده شروع می‌شود.
- GitHub Actions دو ماتریس Node 22.23.5 و 24.22.3 دارد؛ Job جداگانه Docker تصویر را می‌سازد، در یک کانتینر non-root با root filesystem فقط‌خواندنی می‌نویسد، آن را حذف می‌کند و با Volume قبلی اطلاعات را پس از Restart می‌خواند.
- الگوی Nginx TLS و Rate Limiting، برنامه پایش و هشدار، بکاپ/بازگردانی، نکات کلیدها و مرز اعتماد در `docs/DEPLOYMENT.md` مستند شده‌اند. این الگوها جای استقرار واقعی، صدور گواهی، کنترل Firewall یا مانیتورینگ را نمی‌گیرند.
- خروجی OpenAPI، README انگلیسی، راهنمای فارسی و Changelog با رفتار فعلی هماهنگ شدند.

## محدودیت‌های آگاهانه و ریسک‌های باز

1. `node:sqlite` در محیط اجرای محلی Node 22.16 Experimental گزارش می‌شود؛ برنامه در نسخه 24.22.3 اینجا اجرا نشده است.
2. فقط یک پردازش نویسنده و یک دیتابیس SQLite محلی پشتیبانی می‌شود؛ سیستم Multi-region، HA یا Distributed Audit نیست.
3. داده در برابر مدیر دارای دسترسی کامل به میزبان/DB غیرقابل‌دست‌کاری مطلق نیست. Checkpoint امضانشده تنها با ذخیره مستقل و محافظت‌شده ارزش اثباتی بیشتری دارد.
4. `actorId` ادعای سرویس نویسنده است؛ احراز هویت کاربر نهایی و Zero Trust اختصاصی پیاده‌سازی نشده‌اند.
5. TLS، firewall/ACL، محدودسازی درخواست، مدیریت/چرخش Secrets، پایش/هشدار دیسک، نگهداری خارج از سایت و اعمال Retention باید در محیط استقرار تکمیل شوند.
6. عددهای دقیق بزرگ و Decimal مالی باید **به‌صورت JSON string** فرستاده شوند؛ binary floating point به‌صورت ریاضی Decimal دقیق نیست.
7. محدودیت `AUDIT_MAX_EVENTS` سقف تعداد رکورد است، نه سهمیه دقیق بایت دیسک. هنگام تکمیل ظرفیت، Ready=503 و Ingest جدید=507؛ داده خودکار حذف نمی‌شود.
8. تطبیق SQL Schema بسیار سخت‌گیرانه است و حتی تغییر فرمت SQL (با عملکرد معادل) را در DBهای قبلاً نسخه‌گذاری‌شده رد می‌کند. مهاجرت رسمی نسخه Schema نیازمند طراحی جداگانه است.

## نحوه راستی‌آزمایی پس از Push

```bash
npm ci
npm run check
npm run e2e:disk
npm run test:coverage
docker build --pull -t audit-trail-ci .
bash scripts/ci-docker-smoke.sh
```

Docker و Nginx تنها در محیطی که نصب و پیکربندی واقعی دارند باید آزموده شوند. تا وقتی Workflowهای `verify` و `docker` در GitHub سبز نشوند، آن‌ها را PASS محسوب نکنید.

**جمع‌بندی:** مشکلات شناسایی‌شده کدنویسی و قرارداد API رفع شده‌اند و آزمایش‌های موجود موفق بوده‌اند. این نسخه نسبت به v1.1.0 از نظر دقت داده، صحت Schema، سازگاری HTTP و آماده‌سازی استقرار بهتر است. «صفر آسیب‌پذیری» یا «Production-Ready» ادعا نمی‌شود.
